Testing permission boundaries in AI agents

Mubarak IbrahimNovember 2026Technical design and engineering practice

Agent safety is not only about whether a model declines an unsafe instruction. It is about whether the surrounding system enforces the right access boundaries when the model takes an action.

The failure mode

Imagine an assistant that can search documents and answer questions. A user is allowed to read public files, but not a restricted file. If authorization exists only in the system prompt, an unexpected model response or malicious instruction inside a retrieved document may still lead to a prohibited tool call.

The resource boundary belongs in the tool or service that returns the data. A model can help decide which tool to request, but the backend must make the final authorization decision.

Designing a minimal test harness

  1. Define synthetic fixtures: create public and restricted documents with deliberately simple labels.
  2. Introduce explicit principals: represent the user and permitted resource scopes separately from the model prompt.
  3. Instrument every tool call: record requested resource, caller identity, authorization decision, and outcome without recording secret content.
  4. Exercise expected access: verify an authorized request succeeds and is included in the audit trace.
  5. Exercise denied access: verify a request for a restricted resource fails even if the model attempts the call.
  6. Test untrusted content: introduce instructions inside a synthetic document that try to redirect the agent to restricted files.

What to measure

A binary “model refused” score is not enough. Record whether the unauthorized tool call was attempted, whether enforcement denied it, whether any sensitive content reached the model, and whether the final response disclosed restricted content. These distinguish behavioral alignment from security enforcement.

Security principle

A tool's access policy should remain correct even when the agent prompt is ignored, bypassed, or misunderstood.

OpenTrust AI

I am exploring this approach in OpenTrust AI, an independently maintained open-source project. The public repository currently contains a threat model, MVP specification, roadmap, and security policy. The runnable security testing implementation is not yet complete, and no accuracy or detection-rate claims are being made.

The planned first release uses synthetic data and reproducible authorization tests before adding framework integrations. Real-world tools and private environments should only be tested with authorization.

Why this matters

For small teams building autonomous systems, clear tests and readable findings are more useful than an unexplained “safe” badge. The goal is to make individual trust boundaries inspectable and improve engineering decisions.
